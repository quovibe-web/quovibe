# v1.7.1

## Fixes

### PP-XML import reported failure on imports that had actually succeeded

Reported via GitHub against a 178-security HUF-base portfolio. The server log
ended with `Import completed. New portfolio created: <id>`; the browser showed
a generic failure and the user had no way to tell the portfolio was there.

The cause was structural rather than a bug in any one place. Converting a large
export takes minutes end to end — the XML converter, then copying the produced
database into place, then applying the schema and the cross-currency backfill to
it — and the upload request was held open for all of it. Every hop between the
browser and the server enforces its own limit on how long a request may sit
without sending anything: a reverse proxy typically cuts at 60 seconds, Cloudflare
at 100, and this route's own socket limit was 120. Whichever hop cut first, the
server never noticed: it kept working and finished the import against a
connection nobody was reading.

**The upload no longer waits for the conversion.** It now returns as soon as the
file has been accepted and checked, and the browser follows the import's progress
separately. A request that completes in milliseconds cannot be cut by any of
those limits, so the fix does not depend on identifying which one was
responsible — and it holds behind any proxy configuration.

- Rejections that can be decided without running the converter — wrong file
  type, oversized upload, not a valid export, encrypted file, another import
  already running — still come back immediately, with the same messages as
  before.
- Failures that only the converter can find — conversion errors, incompatible
  XML, a name that collides with an existing portfolio — arrive once the import
  finishes, again with the same messages.
- If the connection drops while the upload response is in flight, the browser
  reconnects to the running import instead of reporting a failure the server
  disagrees with. If it genuinely cannot tell, it now says the import may still
  be running and to reload and check — rather than asserting that it failed.

### Related diagnostics

- **A timed-out upload now leaves a trace.** The route set a socket limit but
  never listened for it firing, and the runtime tears such a connection down
  silently — which made a server-side cut indistinguishable from a proxy-side
  one in the logs. Both the timeout and a client disconnecting mid-upload are
  now recorded. That limit also now covers only the file transfer, which is all
  it was ever a sensible budget for.
- **Import completion logs its timing breakdown** — converter time versus
  database time — so a slow import can be attributed without guesswork.
- **The import-status endpoint no longer under-reports.** It consulted only the
  converter's lock file, so it answered "idle" for the whole window between
  accepting an upload and the converter starting.
- An upload rejected because another import was already running is now cleaned
  up immediately instead of waiting for the next startup sweep.

## Notes

No schema changes. Existing portfolios are unaffected; this release changes only
how an import is delivered, not what it produces.
